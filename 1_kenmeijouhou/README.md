# 伊東電機販売社 件名情報登録・管理システム（件名情報 登録・管理システム v7）

## プロジェクト概要
伊東電機販売社様向けに試作されていた「件名情報（顧客引き合い情報）」の登録・管理 Web アプリを引き継ぎ、
アップロードいただいた実データ（2026年7月10日時点）を組み込んだ状態で公開できるよう整備しました。

営業担当ごとの案件（件名）情報と、それに紐づく製品明細（ペットネーム／代表形式／数量／手配状況／発注形式種別）を
登録・編集し、需要集計や受注状況の分析ダッシュボードとして活用できる、単一 HTML ファイルの業務支援ツールです。

## 概要説明プレゼンテーション（はじめての方向け）
`presentation.html` — システムの目的・5つのタブの役割・データ保存の仕組み（localStorage）・
GAS（Google Apps Script）を使った複数人共有の仕組み・二段階同期・導入手順・よくあるつまずきポイントを、
reveal.js製のスライド形式（ブラウザ上でPowerPointのようにページ送りできるHTML）でまとめたものです。
矢印キーまたは画面下部の矢印ボタンでページ送りできます。PDF化したい場合は、ブラウザの印刷機能
（印刷先に「PDFに保存」を選択）でPDFとして保存できます。

## 用途説明・操作マニュアル（単独HTML・画面キャプチャ付き）
`manual.html` — 「このシステムは何のためのものか」という用途説明から、①〜⑤各タブの実際の操作方法、
データの保存・共有の仕組み、よくある使い方シーン別ガイド、トラブル時のQ&Aまでを1つのHTMLファイルに
まとめた操作マニュアルです。実際の画面キャプチャ・フロー図・比較表を多用し、はじめてこのシステムに
触れる方でも迷わず使えるように構成しています。ブラウザで `manual.html` を直接開くだけで閲覧できます
（目次からのジャンプリンク・ページ内アンカー対応）。

### 追加の不具合修正・機能追加（2026-10-21・引き続き未本番反映）
上記8項目のプロトタイプ実装後、動作確認の中でご指摘・ご依頼いただいた内容に対応しました。

9. **不具合修正：「発注予定仕様見込品型番」ドロップダウンが一度選択すると選び直せない**：
   ブラウザ標準の `<input list>`+`<datalist>` の仕様により、入力欄に既存値がある状態だと
   その値に部分一致する候補のみに絞り込まれてしまう問題（従来の「納入予定月」と同じ原因）が
   ありました。該当の入力欄にフォーカス時は値を空にして全候補を表示し、何も選択されずに
   フォーカスが外れた場合のみ元の値に戻す、という対策を追加しました。
10. **UI改善：吊具ドロップダウンの「（旧登録値）」表示を削除**：発注予定仕様見込品型番を変更して
    吊具の候補が変わった際、以前は変更前の値を「（旧登録値）」として特別表示していましたが、
    これを廃止し、新しい候補に一致しない場合は単純に未選択（空欄）に戻すよう簡素化しました。
11. **新機能：吊具欄の「選択／自由入力」切替**：②納入明細（子）の「吊具」列ヘッダー横に
    「選択」「自由入力」のラジオボタンを追加しました。既定は「選択」（ドロップダウンから候補を
    選ぶ）で、「自由入力」を選ぶとテキスト入力に切り替わります。切替は明細行すべてに一括適用
    されます（行ごとの個別切替はありません）。修正画面を開いた際、保存済みの吊具値が現在の
    候補に存在しない（＝自由入力で登録された過去データ）場合は、自動的に「自由入力」モードに
    切り替えて値を保持します。
12. **新機能：⑤メンテナンスのドロップダウン項目リストの外部ファイル入出力**：
    ⑤メンテナンス → 「ドロップダウン項目メンテ」タブに3つのボタンを追加しました。
    - **📤 項目リストをファイルに出力**：`MASTER`（担当・受注確率・手配状況・ペット⇄代表形式・
      発注予定仕様見込品番対比表（吊具１〜３含む）・グループ・担当グループ）のみをJSON形式で
      ファイルダウンロードします。**件名データ（CASES）・パスワード・GAS連携設定は対象外**です。
    - **🔀 ファイルを読込（マージ）**：読み込んだファイルの内容を、現在のドロップダウン項目リストに
      **統合**します。単純な文字列一覧（担当・受注確率・手配状況・グループ）は和集合（両方の値を
      保持）、対応表（ペット⇄代表形式・発注予定仕様見込品番・担当グループ）はキー単位で突き合わせ、
      同じキー（同じペットネーム等）があればファイル側の値で上書きします。既存データは消えません。
    - **♻️ ファイルを読込（差し替え）**：ファイルに含まれる項目を、現在のリストと完全に置き換えます
      （ファイルに含まれない項目は変更しません）。
    - いずれの読込も実行前に内容の異なる確認ダイアログを表示し、誤操作を防止しています。
    - ⚠ **検討の経緯**：当初は「全消去ボタン」を別途設ける案もありましたが、消去してから読込までの
      間に①登録・修正画面が操作不能になる（担当・受注確率・ペットネーム等の選択肢が空になり新規
      登録や既存値の変更ができなくなる）リスクがあったため採用を見送り、読込処理自体に「マージ」
      「差し替え」の2モードを持たせる現在の方式としました。なお、インポートで対応表から特定の行を
      削除しても削除トゥームストーン（`markMasterDeleted`）は記録されないため、その後にGAS同期を
      行うとサーバー側に残っている古い行が復活する可能性がある点は引き続き注意が必要です。
13. **仕様変更：ドロップダウン項目リスト（MASTER）のGAS同期を「管理者専用の反映」経路に一本化**：
    ④サーバー連携設定で一般ユーザーが行う通常の同期（送信・取得）と、⑤メンテナンスでのマスタ編集
    （上記12の内容）を両立させるため、以下のようにサーバー連携の設計を変更しました。
    - **通常の同期（①～④のどの画面から行っても）は、ドロップダウン項目リスト（MASTER）に一切
      触れなくなりました。** 送信（push）時はMASTERをサーバーへ送らず、取得（pull）時は常に
      **サーバー側のMASTERをマージせずそのまま丸ごと採用**します（＝一般ユーザーの同期では常に
      サーバー側のマスタが正）。件名データ（CASES）の双方向マージは従来通り変更ありません。
    - **⑤メンテナンス → ドロップダウン項目メンテ タブに、管理者専用の「👑 サーバーへの反映
      （管理者専用・ドロップダウン項目リストのみ）」セクションを新設**し、「⬆ このドロップダウン
      項目リストをサーバーへ反映（置き換え）」ボタンを追加しました。このボタンを押すと、現在の
      ローカルのMASTER内容を**マージせずサーバー側へ完全に置き換え送信**します（件名データ・
      パスワードには触れません）。これが、編集・インポートしたマスタ内容をサーバーへ反映する
      唯一の経路です。
    - サーバー側（`gas/Code.gs`）に、この専用更新のための新アクション `action:"save_master"`
      を追加しました（既存の `action:"save"`（通常同期）・`action:"overwrite"`（全消去上書き）
      とは別の、MASTERのみを対象とした専用エンドポイントです）。この変更を反映するには
      `gas/Code.gs` の再デプロイが必要です。
    - ⚠ **検討の経緯**：当初「ユーザーの同期は常にサーバー側マスタで丸ごと差し替え」とする案を
      検討しましたが、これを一般ユーザー・管理者を区別せず全員の同期操作に一律適用すると、
      管理者自身がマスタを編集してサーバーへ反映しようとした際にも同じ「サーバー側が勝つ」挙動が
      働いてしまい、**管理者の変更がサーバーへ届く手段自体が無くなる**という矛盾が生じることが
      判明しました。そのため、「一般ユーザーの同期」と「管理者のマスタ反映」を明確に別の操作
      （別のボタン・別のサーバーアクション）に分離する現在の方式を採用しました。
    - ⚠ **残る注意点**：複数の管理者がほぼ同時にマスタを編集した場合、後から「サーバーへ反映」を
      押した方の内容で先の変更が完全に上書きされます（マージされません）。マスタ編集は基本的に
      単一の管理者が行う運用を想定しています。
14. **不具合修正：①画面のCSV書き出し（明細展開・全件／絞込結果のみ）が②明細の見出し変更・吊具列
    追加に未対応だった点を修正**：上記8項目のプロトタイプ変更（②明細の見出し「発注予定正式形式」
    →「発注予定仕様見込品型番」への変更、吊具列の追加）後も、CSV書き出し機能の列見出し・出力内容が
    旧仕様のまま（旧見出し名のまま、吊具列が存在しない）になっていた不具合を修正しました。
    `CSV_DETAIL_HEAD`（CSV列見出し定義）の該当列名を新名称に変更し、末尾に「吊具」列を追加、
    各明細行のデータ生成処理（`casesToDetailsCsvText`）にも明細の`tsurigu`値を出力するよう
    修正しました。この修正は「⬇ CSV書き出し（明細展開・全件）」「⬇ CSV書き出し（明細展開・
    絞込結果のみ）」の両方に共通で適用されています（内部的に同じ関数を共用しているため）。

### ⚠ Hosted Deploy後に必要な別作業（GASを使っている場合のみ）
サイト本体（`index.html`等）のHosted Deployは、別サービスであるGoogle Apps Script側には
影響しません。既にGAS連携で複数人同期を運用中の場合は、Hosted Deploy後に別途、
最新の `gas/Code.gs` を既存のGASプロジェクトに貼り直して「新バージョン」として
再デプロイしてください（手順は `gas/README_DEPLOY.md` 内の該当セクションを参照）。
これを行わない間は、通常の同期（送信・取得）は引き続き問題なく動作しますが、
新しい「👑 サーバーへの反映」ボタンのみ「不明なアクション: save_master」エラーになります。

  - **納入予定月の入力欄**：新規登録・修正のどちらでも、入力欄をクリック（フォーカス）すると
    **常に「今日から前3ヶ月〜後18ヶ月」の計22件の候補**がドロップダウン表示されます（修正時に

    範囲外の場合は**「現在からあまりにも納入予定時期が離れた件名です。入力できません。」**と
    ポップアップ表示したうえで元の値に戻し、登録を受け付けません。

  - JSON書き出し（全件）／CSV書き出し（明細展開・全件）／CSV書き出し（明細展開・絞込結果のみ）／

## データ保存の仕組み（重要）
本アプリは **静的サイト + ブラウザのlocalStorage** で動作する設計です（サーバー側DBは使用していません）。
- `kenmei_cases_v7` … 件名（案件）データ本体
- `kenmei_master_v7` … ドロップダウン・マスタ（担当／受注確率／手配状況／ペットネーム対比表等）
- `kenmei_pw_v7` … メンテナンス画面の管理者パスワード（初期値: `4613191688`）
- `kenmei_deleted_v7` … 件名データの削除トゥームストーン（GAS同期用、id→削除日）
- `kenmei_master_deleted_v7` … ドロップダウン・マスタの削除トゥームストーン（GAS同期用、
  マスタ項目のフィールド名→識別子→削除日）

**複数人での共有・引き継ぎについて：** localStorageはブラウザ・端末ごとに独立しているため、
このままでは「他の人が見ても同じデータが見えない」状態です。運用時は、①各自の端末で編集→
「⬇ JSON書き出し（全件）」→ 誰か1人が「⬆ データ取込（マージ）」で集約、という運用を想定した
作りになっています（`updatedAt` が新しい方を採用してマージします）。

## GASサーバー連携（複数人でのデータ共有）
本アプリは既定では localStorage のみで動作しますが、**Google Apps Script（GAS）をオプションの追加バックエンド**
として設定することで、複数人が同じデータ（Googleドライブ上のJSONファイル1つ）にアクセス・更新できるようになりました。

- **設定場所**（いずれも同じ設定・同期状態を共有）
  - ④ サーバー連携設定（専用タブ、①URL設定／②同期の実行／③ローカル全消去→サーバー取得）
  - ① 件名一覧・登録/修正 → 「＋ 新規件名を登録」フォーム最下部（「キャンセル」ボタンの右に半角分程度の
    スペースを空けて「今すぐサーバーへ送信・同期」ボタンのみを配置。この画面では「サーバーの内容を取得して
    統合」ボタンは表示しません。フォームを離れずその場で送信できます）
  - ⑤ メンテナンス → 「サーバー連携(GAS)」サブタブ（①URL設定／②同期の実行／③ローカル全消去→サーバー取得に
    加え、**④サーバー全消去→ローカル取得（このサブタブのみに設置）**、ファイルのダウンロード欄も掲載）
- **必要なファイル（アプリ内からダウンロード可能）**
  - `gas/Code.gs` … GASウェブアプリ本体（doGet/doPost、Googleドライブへの読み書き、マージ処理）
  - `gas/appsscript.json` … GASのマニフェスト（ウェブアプリのデプロイ設定）
  - `gas/README_DEPLOY.md` … Google Apps Scriptプロジェクトの作成からデプロイ・本アプリへの設定までの手順書（日本語）
- **アーキテクチャ**：localStorageを主体としたオフライン動作を維持しつつ、GASを「追加の同期レイヤー」として
  利用する構成です。GAS未設定でも、これまでと同様に単独利用できます。
- **データ保存先**：デプロイした方のGoogleドライブのルートに置かれる `kenmei_data_v7.json` 1ファイル
  （件名データ・マスタ・パスワード・削除記録をまとめて保存）
- **同期・マージの仕組み**
  - 競合時は `updatedAt`（更新日時）が新しい方を採用（既存のJSON手動取込マージと同じ考え方）
  - 件名データの削除は「削除記録（トゥームストーン、`deletedIds`）」で管理し、他端末の古いデータの
    再送信で削除済みレコードが復活しないようにしています
  - **⑤メンテナンスのドロップダウン項目マスタ（受注確率・手配状況・営業担当＋所属グループ・
    ペットネーム⇄代表形式・ペットネーム⇄発注予定正式形式）の削除も、件名データと同様の
    「削除トゥームストーン（`masterDeletedIds`、localStorageキー `kenmei_master_deleted_v7`）」で
    管理しています。** これにより、ある人がドロップダウン項目を削除した後にサーバー同期しても、
    他の人の端末やサーバーに残っている古いコピーとマージされて削除項目が「復活」してしまうことが
    ありません（項目ごとに削除日を記録し、後から同じ項目名を再登録・編集した場合は削除記録が
    自動的に解除されます）。「初期値（共有エクセル由来）に戻す」ボタンを押した場合は、一括復元
    とみなしてマスタの削除記録をすべてクリアします。
  - 「保存操作のたびに自動送信する」を有効にすると、件名登録・削除・マスタ編集・パスワード変更などの
    操作から約2.5秒後に自動でサーバーへ送信されます（`afterLocalSave()` フック経由）
  - 「今すぐサーバーへ送信・同期」「サーバーの内容を取得して統合」ボタンでの手動同期も可能
  - 「接続テスト」ボタンでURL設定の動作確認が可能
  - **「③ ローカルを全消去してサーバーから取得（上書き同期）」**：②の「サーバーの内容を取得して統合」は
    ローカルとサーバーの内容を`updatedAt`でマージしますが、こちらはマージせず、**このブラウザの
    localStorage（件名データ・マスタ設定・削除トゥームストーン等）を一旦すべて消去した上で、
    サーバー上の最新データのみを取得して置き換える**専用ボタンです。実行前に確認ダイアログが表示され、
    未送信のローカル変更がある場合は失われる旨を警告します。「① 接続テスト」で接続確認 → 必要な
    ローカル変更があれば先に②で送信 → その後この③を使う、という流れを想定しています。
    （④サーバー連携設定タブ、⑤メンテナンス→「サーバー連携(GAS)」サブタブの両方に設置）
  - **「④ サーバーを全消去してローカルから取得（上書き同期）」**（**⑤メンテナンス→「サーバー連携(GAS)」
    サブタブのみに設置**、④サーバー連携設定タブには非表示）：③とは逆方向の操作です。**サーバー上の
    データを一旦すべて消去し、このブラウザ（ローカル）の内容で完全に上書きする**専用ボタンです。
    マージは行われず、他の利用者がまだサーバーへ送信していない変更やサーバー上にのみ存在するデータは
    すべて失われます。他の利用者にも影響する操作のため、実行前に確認ダイアログで警告した上で実行します。
    サーバー側（`gas/Code.gs`）に新設した `action:"overwrite"` エンドポイント（マージ処理を行わず
    送信されたデータで完全に置き換える）を呼び出します。既存のGASデプロイをお使いの場合は、
    この機能を使うために `gas/Code.gs` を最新版に更新・再デプロイする必要があります。
  - **不具合修正：「② 同期の実行」がサーバー側データを消してしまうように見える問題への対応**：
    Googleドライブは同名ファイル（`kenmei_data_v7.json`）の重複作成を許可するため、GASの再デプロイ・
    動作確認を繰り返す過程で同名ファイルが複数できてしまうと、サーバー側スクリプトがそのうち
    「どれを読み書きすべきか」を毎回の呼び出しで検索し直しており、たまたま空／少量データの
    重複ファイルを参照してしまうことがありました。この場合、②の同期（マージ）が「サーバー側の
    データがほとんど空の状態」で行われるため、結果的に送信したローカルの内容だけが反映され、
    「サーバーが消去された後に同期された」ように見えていたと考えられます。
    対応として、`gas/Code.gs` の対象ファイル検索処理を修正し、①一度特定したファイルのIDを
    スクリプトプロパティに固定保存して以後は必ず同じファイルを参照する、②初回のみ・同名の
    重複ファイルが見つかった場合は内容を確認し件名データ（`cases`）の件数が最も多いものを
    正として選ぶ、という仕組みに変更しました。**この修正を反映するには、更新した `gas/Code.gs` を
    再度Google Apps Scriptプロジェクトに貼り付けて再デプロイする必要があります**（`gas/README_DEPLOY.md`
    にトラブルシューティング項目として詳細と、既に重複ファイルができてしまっている場合の
    手動での確認・削除手順を追記しました）。なお、この原因はコード上のレビューから最も可能性が高いと
    判断したものであり、開発環境からライブのGAS/Googleドライブ環境を直接確認することはできないため、
    再デプロイ後に実際に改善するかご確認をお願いします。
  - **追加の安全装置（②同期時の異常な件数減少を検知して自動ブロック）**：上記のファイル重複対策を
    行った後も、原因を問わず「②今すぐサーバーへ送信・同期」の結果、統合後の件名件数が同期前の
    サーバー側件数・この端末の送信件数のどちらよりも大幅（50%以上）に少なくなる場合は、
    `gas/Code.gs`側で**書き込みそのものを中止**するようにしました（サーバー・ローカルとも
    データは変更されません）。中止時はブラウザに「⚠ 安全装置により同期を中止しました」という
    アラートが表示され、診断情報（サーバー側件数／送信件数／統合されるはずだった件数／
    消えかけていた件名の例）が確認できます。
  - **真の原因の特定と自己修復ロジックの追加（②同期バグの最終対応）**：上記の安全装置により、
    実際にユーザー環境で発生した事象を確認したところ、サーバー側・端末側の両方が同じ364件の
    件名データを正しく保持しているにもかかわらず統合結果が0件になる、という診断結果が得られ、
    真の原因を特定しました。原因はGoogleドライブのファイル重複ではなく、**「削除記録
    （トゥームストーン、`deletedIds`）」に、実際には削除されていない件名IDが誤って記録され続けて
    いたこと**でした（一時的な「全案件削除」操作の後にバックアップからデータを復元した際、
    復元データの更新日が削除記録の日付より古いままだったことなどが想定される経緯です）。
    この状態では、通常のマージロジックが「削除記録にあるIDは、更新日が削除日より新しくない
    限り除外する」と判定し、サーバー・端末の両方に正常に存在するデータまで除外してしまいます。
    対応として、`gas/Code.gs`（サーバー側 `mergeCases_`）・`js/gas-sync.js`（クライアント側
    `mergeCasesClient`）の両方のマージ処理に**自己修復ロジック**を追加しました。サーバー側・
    端末側の**両方**が、あるIDのデータを「現存データ」として送ってきている場合、それは
    「本当は削除されていない」という強い証拠とみなし、その削除記録を自動的に無効化してデータを
    保持するようにしています（一方にしか存在しないIDについては、これまでと同様に正しく削除が
    反映されます）。この対応・上記の安全装置は、いずれも`gas/Code.gs`・`js/gas-sync.js`の更新分
    のため、反映には`gas/Code.gs`の再デプロイが必要です（`gas/README_DEPLOY.md`にも詳細を
    追記済み）。
  - **同種の不整合を⑤ドロップダウン項目メンテ（MASTER）側にも発見・修正**：件名データ（CASES）に
    実施した自己修復ロジックは当初、件名データのみに適用されており、**⑤メンテナンス→
    「ドロップダウン項目メンテ」で管理する営業担当・受注確率・手配状況・ペットネーム⇄代表形式・
    発注予定正式形式・所属グループ等（`MASTER`、削除記録は`masterDeletedIds`）には未反映**でした。
    このため、ある端末に古いマスタ項目の削除記録が残っていると、他の担当者がその項目を追加・
    復元して②同期しても、その端末が同期した時点でサーバー側JSONからその項目が再び除外され、
    「サーバーへ送信・同期しても一部の担当者だけドロップダウンリストが更新されない」という
    不整合が発生する可能性がありました。対応として、`gas/Code.gs`の`mergeMaster_()`・
    `js/gas-sync.js`の`mergeMasterClient()`の両方に、件名データと同じ「サーバー・端末の両方に
    現存する項目の削除記録は自動的に無効化する」自己修復ロジックを追加しました。この修正の
    反映にも`gas/Code.gs`の再デプロイが必要です。
  - **最終更新日時（`updatedAt`）を「日付のみ」から「日本時間・分秒まで」に精度向上**：従来、
    件名データの`updatedAt`は`toISOString().slice(0,10)`によりUTC基準の「日付のみ」
    （例: `2026-09-11`）で記録されており、2つの問題がありました。①UTCとJST（日本時間）には
    9時間の差があるため、日本時間の深夜0:00〜8:59に保存すると、UTC上ではまだ前日扱いとなり、
    更新日が実際には変わったのに前日のままに見える。②同期時のマージ判定（`updatedAt`が新しい方を
    採用）が日付単位でしか行えないため、同じ日に複数人が同じ件名を別々に編集して同期すると、
    実際の編集順序に関わらず「後からサーバーに届いた方」で他の変更が丸ごと上書きされ、
    気づかないうちに一方の変更が消えることがありました。対応として、`index.html`に日本時間
    （Asia/Tokyo）で「YYYY-MM-DD HH:mm:ss」形式（分秒まで・ゼロ埋め固定桁数）の日時文字列を
    生成する関数（`nowJstStr()`）を追加し、件名保存時（`collectCase()`）の`updatedAt`を
    この形式に変更しました。マージ判定側（`gas/Code.gs`の`mergeCases_`・`js/gas-sync.js`の
    `mergeCasesClient`）は、桁数を固定した文字列比較（`>=`）のままで時系列順序が保たれるため
    変更不要ですが、削除記録（`deletedIds`、日付のみで記録）との前後判定部分のみ、`updatedAt`の
    先頭10文字（日付部分）を切り出して比較するよう修正し、削除トゥームストーンの判定基準
    （削除翌日以降の再登録のみ復活を許容する、という従来の挙動）を変えないようにしています。
    改修前（日付のみ）のデータと改修後（日時）のデータが混在しても、先頭10文字の形式が
    共通しているため、同じ日付内では「時刻情報を持つ側がより新しい」と判定される形で
    問題なく共存し、データ破損等には至りません。CSV書き出しの列見出しも「最終更新日」から
    「最終更新日時」に変更しています。
  - **二段階同期（レースコンディション対策）**：削除した件名が、削除した本人以外の端末で
    同期後もローカルに残ってしまう場合があるとのご報告を受けて調査した結果、以下の原因を
    特定しました。GAS側は`LockService`により「同時に2件の保存処理が同時実行されない」ことは
    保証していますが、「先に操作した人の処理が必ず先に完了する」ことまでは保証していません。
    このため、ほぼ同時刻に複数の利用者が同期操作を行うと、ネットワーク遅延等により**後から
    操作した人のリクエストの方が先にサーバーに到達・処理されてしまう**ことがあります。この
    場合、先に処理された側は「まだ他の人の変更（削除等）が反映される前の一瞬のサーバー状態」を
    取得してしまい、そのままローカルに反映して同期を終えてしまいます（サーバー自体は最終的に
    正しい状態になりますが、その端末だけ古い状態のまま残り続けます）。この現象を軽減するため、
    `js/gas-sync.js`の「今すぐサーバーへ送信・同期」（`gasSaveToServer`）「サーバーの内容を
    取得して統合」（`gasLoadFromServer`）のいずれかが正常に完了した**約4秒後、もう一度
    サーバー状態を静かに（画面表示なしで）確認・再取得し直す「二段階同期」**を追加しました。
    ほぼ同時に発生した他の利用者の変更も、この確認取得のタイミングまでにはサーバーへの
    書き込みが完了している可能性が高いため、取りこぼしを大幅に減らせます。確認取得自体は
    さらに次の確認取得を予約しないため、無限ループにはなりません。自動テストにより、
    「送信直後は削除前の古い状態を受け取ってしまうが、約4秒後の確認取得で正しく削除後の
    状態に修正される」という一連の動作を確認済みです。この改修は`js/gas-sync.js`のみの
    変更のため、`gas/Code.gs`の再デプロイは不要です（サイトの再公開のみで反映されます）。

## データモデル
### MASTER（マスタ情報）
| フィールド | 型 | 内容 |
|---|---|---|
| owners | array<string> | 営業担当一覧 |
| prob | array<string> | 受注確率区分（受注/A/B/C/失注/納品済） |
| status | array<string> | 手配状況区分 |
| pairs | array<object> | ペットネーム⇄代表形式の1:1対応表 |
| forms | array<string> | 発注予定正式形式の候補一覧 |
| formMap | array<object> | ペットネーム⇄発注予定正式形式⇄種別の対比表 |
| groups | array<string> | 営業担当の所属グループ（1G/2G） |
| ownerGroups | array<object> | 営業担当と所属グループの紐付け |

### CASES（件名データ、1件名=1レコード）
| フィールド | 型 | 内容 |
|---|---|---|
| id | string | 件名の一意ID |
| kenmei | string | 件名名称 |
| kenmeiNo | string | 件名No.（任意） |
| owner | string | 営業担当 |
| prob | string | 受注確率 |
| memo | string | 備考 |
| iwasaki | bool | 岩崎手配(キーイン)フラグ |
| mon | string | 納入予定月（YYYY-MM） |
| updatedAt | string | 最終更新日時（日本時間・分秒まで。形式: "YYYY-MM-DD HH:mm:ss"） |
| details | array<object> | 製品明細（pet/rep/qty/sts/htyp/form） |
